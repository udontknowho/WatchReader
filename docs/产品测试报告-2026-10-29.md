## 一句话结论

下载主链路在番茄系源上跑通了（实测 4.5 章/秒、0 失败）。但三分之二的问题集中在“停不下来”：三方源整本 100% 失败时既不自停，用户也取消不了；删除正在下载的作业只是删了界面，服务会把目录写回来，重启即复活。

## 缺陷清单

下面每条都给出定位与改法。行号基于上面的代码基线，改动前请再对齐一次。

### P0-1 运行中的作业，用户够不到「取消」

**现象**
下载开始后一旦离开进度屏，就再也回不去。三个入口都不给取消：

1. 首页点作业行 → 目录页，主按钮文案变成「下载中…」，点它只弹音提示（`MainActivity.kt:2142` 的 toast「正在下载，进度看通知」），不进进度屏。
2. 目录页 ⋮ 菜单只有「导出 TXT」。
3. 通知没有取消按钮（`buildNotification` 没有 `addAction`），点通知也不会落到进度屏——`openAppIntent()` 塞了 `EXTRA_BOOK_ID`，但 `MainActivity` 全文没有读这个 extra。

**后果** 用户看着一本全失败的书拖着网络，只能等它跑完 2478 章，或去删作业（见 P0-2，删了还会复活）。

**怎么改**（三处，都在 `MainActivity.kt` / `DownloadService.kt`）

1. `startDownload()`（`MainActivity.kt:2132`）把「正在下同一本」从 toast 改成直接进进度屏：

```kotlin
val running = DownloadService.runningBookId
if (running != null) {
    // 以前这里只弹 toast，导致离开进度屏后永远回不去，取消入口也就丢了。
    if (running == info.bookId) { showProgress(info); return }
    toast("正在下载另一本，请稍候"); return
}
```

2. `buildNotification()`（`DownloadService.kt:348`）加一个取消动作，走已有但没人触发的 `ACTION_CANCEL`：

```kotlin
if (ongoing) {
    b.addAction(
        Notification.Action.Builder(
            null, "取消",
            PendingIntent.getService(
                this, 1,
                Intent(this, DownloadService::class.java).setAction(ACTION_CANCEL),
                PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE,
            ),
        ).build(),
    )
}
```

3. `onNewIntent` / `onCreate` 里消费 `DownloadService.EXTRA_BOOK_ID`，点通知直接开进度屏（`openAppIntent()` 的注释已经这么写了，只是没人实现）：

```kotlin
// onCreate 与 onNewIntent 都调一次
private fun openFromNotification(intent: Intent?) {
    val id = intent?.getStringExtra(DownloadService.EXTRA_BOOK_ID) ?: return
    if (DownloadService.runningBookId == id) restoreProgress(id)
}
```

`restoreProgress(id)` 用 `Downloader.restore` 拿 `BookJob`，再 `showProgress(BookInfo(...))` 即可，`showProgress` 内部会读 `DownloadService.runningBookId` 判断是否显示取消。

### P0-2 删除正在下载的作业，作业会复活

**现象**（实测三次都能重现）
在首页 ⋮ →「删除」→「删除」，列表里条目消失。但下载线程没有停，仍在写 `job.json`，把 `deleteRecursively()` 删掉的目录重新建出来。`am force-stop` 重启 App 后，「未命名 · 2478 章 0/2478 · 失败 187」原样回到最近下载。

**根因**
`confirmDeleteJob()`（`MainActivity.kt:2467`）只做了一件事：

```kotlin
File(jobsDir(), JobStore.safeDirName(job.bookId)).deleteRecursively()
```

没有通知服务。`Downloader` 每章结束都会 `persist()`，于是目录重建。

**怎么改**

```kotlin
.setPositiveButton("删除") { _, _ ->
    thread {
        // 先让服务停手，再删目录；否则 Downloader 每章的 persist 会把目录写回来。
        if (DownloadService.runningBookId == job.bookId) {
            DownloadService.cancel(this@MainActivity)
            val t0 = System.currentTimeMillis()
            while (DownloadService.runningBookId != null && System.currentTimeMillis() - t0 < 3000) {
                Thread.sleep(50)
            }
        }
        File(jobsDir(), JobStore.safeDirName(job.bookId)).deleteRecursively()
        // 兜底：极端情况下最后一次 persist 已经排在队列里，删完再确认一次。
        Thread.sleep(200)
        File(jobsDir(), JobStore.safeDirName(job.bookId)).deleteRecursively()
        runOnUiThread { showHome() }
    }
}
```

同时给 `JobStore` 加墓碑保护，彻底断掉复活路径：`Downloader.persist()` 发现目录已被删就自杀（`cancelled()` 返回 true）。最小写法是在 `JobStore.appendChapter` / 快照写入前判断父目录不存在则抛 `CancellationException`，`Downloader` 的 catch 块已把“取消”归为不记失败。

### P0-3 整本 100% 失败，不熔断、不自停、还开机自动续跑

**现象**
书荒荒源的《凡人修仙传》（2478 章，`state=RUNNING`）每次启动 App 都会自动恢复。每章耗时恒定 7.3 s，失败数持续增长：20:52 是 74，21:05 是 187。成功 0 章。源站本身没问题：同 URL `curl` 返回 HTTP 200、13 KB、0.5 s。

**根因**
1. `Downloader` 只在最后统计失败，没有熔断。`Backoff` 只处理单章重试。
2. 失败原因丢失。`Downloader.errKind()`（`Downloader.kt:372`）兜底分支只返回 `e.javaClass.simpleName`，message 被丢掉，日志里只有 `IllegalStateException` 四个字，无法定位。7.3 s 是 4 次尝试 + 1/2/4 s 退避之和，说明是秒失败后重试，不是超时。
3. 启动时无条件恢复 RUNNING 作业（`DownloadService` 的 resume 路径），不看历史失败率。

**怎么改**

a) 熔断（`Downloader.kt` 批次循环，`batch` 跑完后）：

```kotlin
// 连续失败到阈值就整本停下：三方源坏掉时跑满 2478 章只是白烧流量。
val consecutive = fail
if (consecutive >= FAIL_BREAK && ok == 0) {
    abortReason = "连续 $consecutive 章全部失败（${errKind(...)}），已暂停"
    break
}
```

`FAIL_BREAK = 20` 起步，配合批次结束时的进度广播，让进度屏把 `abortReason` 显示出来（现在进度屏没有失败原因的位置，建议加一行红字）。

b) 日志带 message（一行，先改这条，否则后面都白搭）：

```kotlin
else -> e.javaClass.simpleName + (if (m.isNotBlank()) ": ${m.take(80)}" else "")
```

c) 恢复策略：`RUNNING` 状态恢复到前台时，若该书已完成章节数为 0 且失败数超过总章数的 5%，不要自动开跑，改成在首页标「上次失败，点继续重试」。

**定位完记得重测** 这条只治“停不下来”，不治“为什么全失败”。`IllegalStateException` 的真实 message 目前拿不到，先按 b) 补日志，再挑一本同源的书重跑，才能确定是解析、编码还是连接复用的问题。

### P1-1 首页进度是死的

**现象** 首页显示 `553/1650`，同一时刻磁盘里 `job.json` 已经是 842。停在首页不动，数字永远不变，必须离开再进来才刷新。

**根因** `progressReceiver`（`MainActivity.kt:2560`）只在进度屏消费广播；首页视图在 `showHome()` 时一次性构建，之后不更新。

**怎么改** 两条路，选便宜的那条：进度广播到达时，如果当前是 `Screen.Home`，只更新对应行的副标题文本（给 `listItem` 返回的 TextView 留个引用，别重建整屏）；或者退一步，首页每次 `onResume` 重建一次。前者是十分钟的活，后者会闪一下。

### P1-2 三方源的书名、作者全丢

**现象** 天空书屋和玄幻阁的目录页顶栏空白；下载后首页显示「未命名 · 1650 章」；通知标题也是「未命名」。

**根因** `SourceEngine.toc()` 结尾固定返回空名字（`SourceEngine.kt:387`）：

```kotlin
return BookInfo(bookId = book, name = "", author = "", ...)
```

`loadToc()` 拿到后直接 `showToc(pair.second, pair.first)`（`MainActivity.kt:2034`），没有把搜索结果里的 `hit.name` / `hit.author` 回填。番茄源那条路径不经过 `SourceEngine`，所以正常。

**怎么改**（一行，改在 `MainActivity.kt:2034`）

```kotlin
showToc(
    pair.second.copy(
        name = pair.second.name.ifBlank { name },
        author = pair.second.author.ifBlank { author },
    ),
    pair.first,
)
```

注意 `name` 是 `loadToc` 的入参（搜索结果书名），这行之后作业名、通知标题、导出文件名都会跟着正常。

### P2-1 续传后速度与剩余时间虚高

**现象** 续传后进度屏显示 `2190 章/分 · 约 37 秒`，实际约 5 分钟。真实速度 4.5 章/秒（270 章/分）。

**根因** 速度用总数算（`MainActivity.kt:1000`、`:1058`）：

```kotlin
val speed = if (elapsed > 0) " · ${progressDone * 60 / elapsed} 章/分" else ""
```

`progressDone` 是“已完成总数”，续传时它一开始就是 257，而 `elapsed` 从 0 开始计。

**怎么改** `startDownload()` 里记基线：

```kotlin
progressBase = Downloader.restoreLight(jobsStore(), info.bookId)?.count(ChapterStatus.DONE) ?: 0
```

速度改成 `(progressDone - progressBase) * 60 / elapsed`，剩余时间同式换算。

### P2-2 没简介的书也渲染一张只有“…”的卡片

**现象** 玄幻阁的书，目录页顶部有一张卡片，里面只有一个省略号。

**根因** 书源取不到简介时，`loadToc` 用搜索结果的 `abstractText` 兜底（`MainActivity.kt:2000`），而这份兜底值常常是 `"..."` 这类占位。`showToc` 只判 `isNotBlank()`，所以照画。

**怎么改** 判「有意义的简介」而不是「非空」：

```kotlin
val meaningfulIntro = info.intro.trim().let {
    it.isNotBlank() && it.count { c -> c.isLetterOrDigit() } >= 10
}
if (meaningfulIntro) { ... }
```

### P2-3 重复导出会在系统文档里堆副本

`导出 TXT` 连点两次，得到 `神通者 - 天蚕土豆 (1).txt`、`(2).txt`。App 私有目录那层按 `(k)` 自增，发布到 MediaStore 时系统再加一层 `(1)`，两份都在，1.4 MB 一份。

**这是设计行为**：设置页明确写着「文件名：书名 - 作者.txt（重名自动加 (2)）」。所以不算 bug，但连点三次就有三份 1.4 MB 副本，手表存储紧张。建议发布前按 `DISPLAY_NAME` 查重，存在则覆盖。

**怎么改** 发布前用 `MediaStore` 查一次同名 `DISPLAY_NAME`，存在就覆盖（`ContentResolver.update` + `openOutputStream`），或至少把 `(1)` 的情况在 toast 里说清楚。

### P2-4 版本号默认值没跟上

`build.sh:23-24` 仍是 `APP_VERSION=1.3.8` / `APP_VERSION_CODE=21`，而线上包是 `1.4.0-beta6` / `28`。README 明确要求每次改动同时改这两个默认值，否则别人直接 `bash build.sh` 就打出旧版本号。

**怎么改** 收尾时统一处理：加一条 `bash build.sh test` 前置检查，读 `app/AndroidManifest.xml` 的 `versionCode` 与 `build.sh` 默认值比较，不等就报错退出。

### P2-5 差 5 章没下完，主按钮就退回「继续下载」

**现象** 1645/1650 章的作业进目录页，主按钮是「继续下载」，导出被降到右侧的小图标 ⤓。全成功的作业（神通者 167/167）主按钮才是「导出 TXT」。用户下完一大半书，最想干的导出反而藏起来了。

**根因** `showToc` 用 `finished = job?.isFinished` 分支（`MainActivity.kt:909` 附近），`isFinished` 只认「零失败」，`state=FAILED`（有失败章）时判成未完成，按钮回到「继续下载」。

**怎么改** 分两种完成态：全成功 → 主按钮「导出 TXT」；有失败但完成率 ≥ 90% → 主按钮仍是「导出 TXT」，旁边加一行小字「5 章失败，点这里重试」把重试降级成次级操作。

### P3 待观察（不阻塞发版）

- 取消按钮没有二次确认，误触即停（已下载章不丢，可接受）。
- 取目录 10–20 s 期间只有沙漏，建议把「取目录」和「试读校验」拆成两段文案，让用户知道还在动。
- 「删除下载」确认框写「将删除全部正文」，0 章作业也这么写，容易吓人。

### P2-6 表冠三项改了要「下次进入页面才生效」

设置页自己写着「表冠参数在下次进入页面时生效」。用户拨完滑杆，回阅读页发现还是旧手感，第一反应是没保存。改法：滑杆值变化时直接写静态字段（`crownStep`/`crownGlide` 已是内存字段），只把「重启 App 生效」的部分留在提示里；或者干脆在离开设置页时重建一次阅读页。

### P2-7 每屏 78 字，一章 30 屏

默认字号 16 sp + 行距 1.75，在 378 px 宽的屏上只有 6 行。手表上可读性没问题，但一章要翻 30 多次。建议行距默认降到 1.5，或给阅读页一个「紧凑」开关（行距 1.35 + 字号 14），把每屏提到 8–9 行。这条是口味问题，不改也行，但要知道用户为什么觉得「一屏看不了几个字」。

### 待定性：玄幻阁跑完 1645 章后整站不再响应（10-30 下午已定性，见第三轮）

跑完这本书后再测，`www.xuanhuange.info` 的首页与章节页都连不上：TCP 10 s 无字节，DNS 正常（172.247.2.131），同期 baidu 200 / 0.55 s。无法区分「站点限流」和「站点故障」，因此那 5 章失败的原因**尚未定性**。两个方向的产品要求一致：失败要写清原因（见 P0-3-b），连续失败要熔断。

若证实是限流，还需要一条：单源节流（并发 4 → 2，或按站点插 200 ms 间隔）。现在 4 条通道全速跑 1650 章，没有任何退让。

### P2-8 书源页能看不能改，写着「启用/禁用」的地方没有开关

**现象** 设置页那一行是「管理书源 / 启用/禁用与导入」（`MainActivity.kt:2386`），点进去只有：书源市场、更新书源库、下载线程、本地书源卡片、全部书源列表。列表每一行只有 ✓/⚠/✗ 图标 + 名称 + 不可用原因，**点不动**，没有开关，也没有「测试」按钮。用户看到 53 条里写着「3 条暂不可用」，能做的只有看着。

**根因** 列表行是 `Widgets.listItem(...)`（`MainActivity.kt:1290` 附近），没有 onClick；全仓库没有任何 `Switch` / `CheckBox` 组件。`enabled` 字段只在导入侧被读一次（`LegadoImport.kt:50`，false 时返回「源已禁用」并丢掉规则），界面从没暴露它。

**后果** 用户唯一的停用手段是改 `/data/data` 下的 JSON（需 root 或 adb）。反过来，源站挂了、搜出来全是垃圾的源，也没法让程序少发请求。

**怎么改** 最小改动：列表行加一个开关，写回 `sources/legado.json` 的同一条 `enabled`，重启后生效即可（`LegadoImport` 已经认这个字段）。次优：行内点开是详情，详情里给「停用 / 删除 / 测试」。

### P2-9 53 个源只搜 15 个，用户不知道是哪 15 个

**现象** logcat 每次搜索都会写：`源共 53 个，搜索用前 15 个，其余 38 个仅备用`（`MainActivity.kt:90`）。界面上完全没有这层信息：书源页写「可用 53 / 共 53 条」，用户理解为「这 53 个都会参与搜索」，实际七成不参与。刚导入一条新源，如果它排在 16 位之后，搜索结果里永远不会出现它，且没有任何提示。

**佐证** 把「快眼看书#bybk.cc」改成 `enabled:false` 后，书源页可用数 53→52，但搜索侧的 `源共 N 个` 仍是 53，两套计数互不对应；该源也从未出现在 per-source 命中日志里（它在 15 名之外），所以「停用后搜索结果变少」这件事在运行时根本观察不到。

**怎么改** 两条都要：①书源页把「参与搜索的 15 个」单独分组置顶并标出序号，其余标「备用（不参与搜索）」；②给用户一个「让这个源参与搜索」的动作（置顶 / 提高权重），否则导入再多源也没用。

### 玄幻阁那 5 章：不是限流，是目录脏数据（高置信，未终验）

先复核站点：`www.xuanhuange.info` 今天仍然 TCP 能连、20 秒 0 字节（首页与章节页一致，连已下成功的 `3448246.html` 也没有响应）；DNS 解析到 172.247.2.131（xuanyge.com.bbqcdn.com），ICMP 221 ms，同期 baidu 200 / 0.58 s。**站点侧 hang，不是本地网络**，所以仍无法取页面终验。

再看 `job.json` 本身，答案在目录里：

| itemId | 标题 | 状态 |
|---|---|---|
| …3450041 | 第一千六百二十三章 双帝之战！（下） | DONE |
| **3450042** | **第一千六百二十四章 结束，也是开始。(大结局)** | DONE |
| 3450043 | 第九十四章 | FAILED |
| 3450045 | 第两百九十五章 | FAILED |
| 3450047 | 第三百八十五章 | FAILED |
| 3450048 | 第三百九十六章 | FAILED |
| 3450049 | 第一千零十章 | FAILED |

三条依据：①大结局已经是第 1645 章，后面再没有正文；②这 5 条的标题不符合本书编号体系（本书用「二百」，它们是「两百」），像是从目录页的推荐位 / 最新更新区块抓来的别书链接；③章节 id 从 3448246 连排到 3450049，却**缺 3450044 和 3450046**，正是「东一条西一条捡来的链接」的形状。

结论：这 5 章失败是**目录解析收了非本章节的链接**，与限流无关，重试当然也不会成功。产品侧要求不变：失败要写清原因（P0-3-b），连续失败要熔断。**未终验的部分**：等站点恢复后取一次 `3450043.html`，确认返回的是 404 / 别书章节，才能把「高置信」改成「已证实」。

**本轮阻塞（已排除）** 13:29 之后画面全黑、宿主刷 `pixelcopy result=3`（ERROR_SOURCE_INVALID）。**不是虚拟屏坏了**：17:5x 重新 `am start --display 9` 后同一套工具立即正常（截帧、点击、滑动、导出全可用）。真实原因两条：

1. **App 进程不在跑**。17:50 查 `pidof com.watchdl` 为空，虚拟屏上只剩容器层（`dumpsys SurfaceFlinger --list` 只有 `Display 9 name="vd-host"`，没有 watchdl 的窗口层）——没内容可合成，抓帧当然是黑的。之前每次黑屏都发生在 `am start` 报 `Complete` 之后，实际进程已不在。
2. **窗口失焦后首次点击只用于取焦点**。手机上用到别的 App 时，虚拟屏里的 Activity 被顶掉（实测 `topResumedActivity` 变成微信）；此时屏幕上画的是上一帧，第一次 tap 不生效，得先 tap 一下再操作。

结论：虚拟屏宿主的抓帧链路没问题，但**它依赖一个自己管不隷的生命周期**：手机一被使用，虚拟屏里的应用随时会被挂起，画面冻结在最后一帧。做自动化测试前必须先验三件：`pidof` 有值、`topResumedActivity` 是本应用、截一帧不是全黑。

搜索空态与导出的实测结论：

- 空输入点「搜索」：`MainActivity.kt:1873` 只弹 toast「请先输入书名」，对话框不关闭。实测截图与点击前提一致，确认不跳页。
- 搜到 0 条的三种文案（`MainActivity.kt:839-847`）本轮**没触发到**，见 P2-10。

### P1-4 每章开头夹 7 行别书书名，阅读器和导出文件都有

**现象** 打开玄幻阁那本书的第 3 章、第 11 章，正文上方都是同一小串：「抵死不说我爱你 / 林炎柳幕妍 / 林炎柳幕妍 / 镇守府求生指北 / 古剑迷踪 / 通天武尊 / 后宫娱乐 / 镇国战神叶君临」，然后才是正文。导出的 TXT 也一样：**1645 章 / 1645 章全部命中**，一章不落。

**根因** 正文提取只取了容器内的全部文本，没剔除源站的推荐位模块。同一套规则也把推荐位链接当成了章节（就是玄幻阁末尾 5 条失败章的死链来源）——两件事是同一个根。

**后果** 阅读时每章开头被 7 行无关书名占掉 3～5 屏（按 P2-7 每屏 78 字算），导出的文件也不能直接分享。用户看不出这是站点的垃圾，只会觉得软件排版差。

**怎么改** 正文提取加一道清理：连续多行、每行短（<20 字）、不含句术标点的行块整块丢掉；或按源站规则里的 `remove` 选择器剔除。同时给下载加内容校验（正文 <200 字、或命中书名列表则不计 DONE）。

### P2-10 搜什么都有一堆无关书，没有相关度也没有空态

**现象**三个实测：

| 关键词 | 结果 |
|---|---|
| 不存在的书名xyz | 212 本（全是别书，快眼看书/番茄模糊匹配） |
| qqzzxxvv | 10 本（全来自番茄） |
| 龘靐齉爩蠡龗 | 59 本，15 源里 11 源响应、4 源失败 |

**后果** 代码里准备了三条「没找到」文案（`MainActivity.kt:839-847`），但实际永远走不到——源站把关键词当模糊字匹配，总能吐回一堆书。用户搜一个不存在的书名，得到 212 本无关结果，界面上没有任何「这些不相关」的提示，也没有按相关度排序。

**怎么改** 结果先按相关度分两栏：书名完全/前缀包含关键词的置顶，其余折起来标「模糊匹配 N 本」。
