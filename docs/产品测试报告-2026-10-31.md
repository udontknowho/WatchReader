## 本轮缺陷

### R1 · P1-4 复现并量化：62% 的章节正文夹热门书单

**现象**
打开「斗破苍穹.2」第 1 章，正文上方是 8 行别书书名与标语，然后才是正文。导出文件同样如此。阅读器第一屏被这 8 行占满，用户看不到正文。

```
魔道妖女重生后，大佬全是我道侣
穿越自带炼妖壶：桀桀，顷刻炼化
百年杂役，我在废丹房捡漏成仙
末世大佬穿星际，四个竹马悔哭了
兽世恋综当恶女？怎么顶流排队亲
词条修仙：从凡女开始叩仙门
血条是倒着的8？那是特喵无限！
道化圣人
```

**量化**
按「正文首个非空行短于 30 字且不含任何句读」判，327 章里 203 章命中，占 62%。各章的推荐书单内容不同，不是同一串固定文本，无法用一条固定字符串匹配掉。

**根因**
书源「玄幻阁吧」（`http://www.xuanhuange.info`）的正文规则是 `#content@textNodes`，把容器内的全部文本节点都收了，包含站点的推荐位模块。该源有 `replaceRegex`，但只覆盖 `随机推荐.*`、`精华书阁.*`、`最快更新.*` 这类广告语，没覆盖书名列表块。`SourceEngine.applyReplaceRegex` 只做一次替换，没有块级清洗。

**为什么不是个例**
10-29 报告里同一站点另一本书（`7_7555_`，1645 章）100% 命中，推荐书单换成另一串（「抵死不说我爱你 / 林炎柳幕妍 / …」）。同一套规则、同一站点，块内容随书变化。所以固定正则修不住，要按形状判。

**怎么改**（三条，建议一起做）

1. 通用清理放进 `Downloader.htmlToText`（`Downloader.kt:653`）：取完行数组后，从头部连续吞掉「短且无句读」的行块，条件是连续 ≥3 行、每行 ≤30 字、不含 `。，！？…：`。吞到第一行正常段落为止。
2. 护栏必须有：53 条书源的真实页面回放，确认不会吃掉「上」「下」「（本章完）」这类合法的短行。当前 `htmlToText` 只处理「首行与次行重复」一种情况（`Downloader.kt:660`），新增块级逻辑要给独立函数并单测。
3. 内容校验：正文剩余字数 <200，或首块命中书名列表，就不记 `DONE`。旧报告 P1-4 已提过这一条，本轮仍然没有。

**坦白一处不足**：我想取原始 HTML 看这个模块的 DOM 结构，以便给出更准的选择器。`www.xuanhuange.info` 现在对本机 0 响应（见 R3），取不到页面。所以上面的改法只能按文本形状做，无法按节点剔除。

### R2 · 导出与阅读的章节标题重复

**现象**
导出文件里每章标题长这样：

```
第1章 正文_第1章：结识神秘老者
第2章 正文_第2章：处于落魄环境
```

序号前缀与原文标题重复，还带着源站的「正文_」前缀。阅读页顶栏同样是 `正文_第1章：…`。

**根因**
`Downloader.convert`（`Downloader.kt:641-647`）拼标题时，只有当标题本身以「第N章」开头才不加序号。本源标题是「正文_第1章：结识神秘老者」，开头是「正文_」，守卫不成立，于是拼成「第1章 正文_第1章：…」。标题里的「正文_」「废柴逆袭_」来自源站目录，属于脏数据。

**怎么改**

```kotlin
// Downloader.kt:644
private val CHAPTER_NO = Regex("""第\s*[零〇一二三四五六七八九十百千万两\d]+\s*[章节回卷篇]""")
val head = if (CHAPTER_NO.containsMatchIn(title)) title else "第${seq}章 ${title.ifBlank { "" }}".trimEnd()
```

把「以第N章开头」放宽成「含第N章」，本源和「废柴逆袭_第22章」这类都能挡住。顺带在展示层去掉 `^[^\s：:]{1,10}_` 这类源站前缀，标题会干净一截。

**风险**：正文标题里偶尔出现「第N章」字样（如「番外 第3章 之后」）会不加序号。序号本来只是辅助定位，可以接受。

### R3 · 定性进展：站点在跑量结束后立刻停止响应

**时间线（本轮实测）**

| 时间 | 事件 |
|---|---|
| 09:16:34 | 开始下载，玄幻阁吧返回正常，约 270 章每分 |
| 09:17:50 前后 | 327 章全部落盘，`state=DONE`，零失败 |
| 09:18:19 | App 内导出 TXT 成功（本地操作，不需网络） |
| 09:2x | Termux 侧 `curl` 同一站点：DNS 正常（172.247.2.131），TCP 20 s 0 字节 |
| 09:2x | 换 4 个本地代理端口重试，全部失败，排除本机代理配置 |

**结论**
站点在本机跑完 327 章后立刻停止响应，前后只隔几分钟。10-30 报告里「跑完 1645 章后整站不再响应」的悬案，本轮补上了「成功下载 → 随即挂死」的短时间线。限流假设置信度提高，站点故障的假设被削弱。仍未终验：没等到站点恢复后复测。

**产品要求**（与旧结论一致，本轮再强调）
单源节流。现在 4 条通道全速跑，一本 327 章的书 76 秒跑完，站点反手就掐断整个 IP。手表端只有一本书要下，慢一点无所谓，被封一次却是整站不可用。

## 复现步骤

```bash
~/vd/vd.sh stop; ~/vd/vd.sh start 378 496 326   # 不带参数会建成 1080x2344，界面全乱
timeout 25 /system/bin/su -c '/system/bin/am start -W -n com.watchdl/.MainActivity --display <id>' </dev/null
~/vd/vd.sh shot ~/vd/state/x.png               # 截图判读
```

界面上的三个坑：

- 搜索要先点搜索框弹出「搜索小说」对话框，再点对话框里的输入框，最后 `paste`。
- 键盘挡住「搜索」按钮时，点键盘右上角的 ∨ 收起。按 BACK 有时会把整个对话框关掉。
- 目录页进来就停在章节列表，要先向**下**滑两次才看到「下载免费章 / 导出 TXT」那张卡片。

对账口径：

```bash
# 作业状态。章节键是 status（DONE/FAILED），不是 done/failed
timeout 30 /system/bin/su -c 'cat /data/data/com.watchdl/files/books/<bookId>/job.json' </dev/null
```

`chapters.jsonl` 按**完成顺序**落盘，不是目录顺序。导出靠 TOC 的 `itemId` 顺序重排，所以按行号读这个文件判断章节顺序会误判。
