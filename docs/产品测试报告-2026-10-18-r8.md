## 二、P0-1 请求卡死打不破

**现象**：斗破苍穹停在 656 章，`state` 一直是 `RUNNING`，三分钟以上零进度。

**证据**：

- 章节文件停在 656 行，`job.json` 三分钟未变；
- 线程栈（`/data/anr/trace_04`）：`Thread-4` 停在 `core/Http.fetch(Http.kt:115)`，即 `conn.responseCode`；
- 看护线程（`Http.kt:107-111`）30 秒到点确实调了 `conn.disconnect()`，**没有解开阻塞**；
- 同期 logcat：`DNS_CACHE: ... result_code:408`。

**根因**：卡点在 DNS 解析。`connectTimeout` 不覆盖 `getaddrinfo`，`disconnect()` 也打断不了阻塞中的解析。r7 的总时限方案只对「慢速吐字节」有效。

**修法**（`Http.kt`）：`fetch` 拆两层。

- `fetchNow`：原实现不动，重定向、逐次压 `readTimeout` 都保留；
- `fetch`：把整个 `fetchNow` 交给 `newCachedThreadPool` 的独立线程，`Future.get(timeoutMs × 2 + 2s)`，超时 `cancel` 并抛「请求超时（含 DNS）」。

池用 cached 而非固定大小：卡死的线程留在阻塞里不退出，固定大小会在几次卡死后把下载冻住。

`Downloader` 配套两处：取消时不再重试；被取消打断的章不记 FAILED。

**回归**：

```
[Http] 卡死连接（连上不回包，旧实现的 disconnect 解不开）
  ✓ 卡死请求在预算内放弃
```

真机：300 章测试作业跑 50 秒，172 章，失败 0，未再出现停滞。

## 三、P0-2 单线程下载

**现象**：斗破 1645 章从 646 爬到 1411 用了两小时，速率 0.17 章/秒。

**根因**：`DownloadService` 里 `concurrency = if (source is FanqieApp) 3 else 1`。通用书源恒为串行；单章请求延迟约 5.8 秒，串行就是 0.17 章/秒。

**修法**：

- `书源` 页新增「下载线程」，可选 1 / 2 / 3 / 4 / 6 / 8，存 `reader` 偏好的 `lanes`，默认 3；
- `DownloadService` 统一读该值，删掉只有番茄开并发的写死逻辑。

**回归**（4 线程，同一本书）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 速率 | 0.17 章/秒 | 2.1 章/秒 |
| 剩余 85 章 | 约 8 分钟 | 40 秒 |

另一次 300 章作业实测 3.4 章/秒（4 线程）。番茄源 1678 章：1075 → 1678 用 60 秒。

**风险**：线程越高越容易触发书源站限流（空正文 → 记失败 → 退避）。8 线程未测。

## 四、P1-3 取消后状态

**现象**：点「取消」后服务确实停了，但 `job.json` 仍是 `"state":"RUNNING"`；重进目录页显示「上次下载已中断（系统回收了后台）」。

**根因**：`ACTION_CANCEL` 只做 `interrupt + stopSelf`，状态靠 `finally` 写 `PAUSED`，且请求在飞时要等很久才写。`CANCELLED` 这个状态在代码里根本不存在。

**修法**：

- `JobState` 新增 `CANCELLED`；
- 取消时先落盘再中断（读 `currentBookId`）；
- `Downloader` 增加 `isCancelled` 判定：不再开新章、`pause()` 吞掉 `InterruptedException`（否则取消会打穿 `run()`，落盘那步走不到）、终态写 `CANCELLED`；
- 每章 `persist` 的默认状态跟随取消标志——否则服务 `stopSelf` 带走进程，终态那次写盘来不及执行，`CANCELLED` 会被每章的 `RUNNING` 盖掉；
- 界面文案分开：`CANCELLED` →「上次下载已取消」，`PAUSED` →「上次下载已中断（系统回收了后台）」。

**回归**：

| 时刻 | `state` | 章数 | 失败数 |
|---|---|---|---|
| 取消前 | RUNNING | 172 | 0 |
| 取消后 2 秒 | CANCELLED | 192 | 0 |
| 取消后 7 秒 | CANCELLED | 192 | 0 |

重进目录页显示「上次下载已取消。点「继续下载」接着跑。」；点「继续下载」接着跑（24 → 44 → 67 章）。

## 五、P1-4 下载中误报中断

**现象**：后台正在下载（820/1645），返回目录页却显示「上次下载已中断」。

**根因**：`showToc` 只看磁盘里的 `job.state`。作业跑着时 `job.json` 一直是 `RUNNING`，`restore()` 把 `RUNNING` 改判成 `PAUSED`，于是正在跑的书页报中断。

**修法**：`DownloadService.runningBookId`（作业开始设、结束清）。同一本书正在跑时不显示中断提示，按钮显示「下载中…」，点击提示看通知。

**回归**：下载中（67/500）返回目录页，无提示，按钮「下载中…」，无重建、无重启。

## 六、P1-5 云端拉取无总预算

**现象**：点「发现榜单」后 20 秒以上停在「正在拉取推荐…」。

**证据**：logcat `DNS_CACHE: hostname:gcore.jsdelivr.net ... result_code:408`；Termux 侧同域名 DNS 20 ms 正常。

**根因**：`RankConfig` 四个镜像串行、每个 12 秒超时；`loadStream` 八条榜串行、每条独立超时。全挂时最长一分半以上，用户看到的就是卡死。

**修法**：

- `RankConfig.load` 加 20 秒总预算，每次请求的超时取 `min(单次, 剩余)`；
- `CloudSource.update` 加 45 秒总预算；
- `loadStream` 加 20 秒总预算。

**回归**：本轮点「发现榜单」6 秒出内容（番茄推荐榜），不再停在加载文案。取不到时显示「推荐暂时取不到，稍后重试」。

## 七、P2-6 版本号注入无效

**现象**：`APP_VERSION=1.0.4 bash build.sh` 打印 1.0.4，装机后 `dumpsys` 仍是 `1.0.0 / code 1`。

**根因**：`aapt2` 的 `--version-code/--version-name` 只在 manifest 未声明版本时生效；`app/AndroidManifest.xml` 写了显式值。

**修法**（`build.sh`）：link 前把 manifest 复制到 `build/AndroidManifest.xml`，`sed` 注入版本号，并断言注入成功；link 指向临时文件。

**回归**：

```
aapt2 dump badging build/WatchDownloader-1.0.6-release.apk
package: name='com.watchdl' versionCode='7' versionName='1.0.6'

dumpsys package com.watchdl
versionCode=7  versionName=1.0.6
```

## 八、P2-7 表冠滚动与 P2-8 虚拟屏

**表冠**：代码里没有 `Rotary`、`AXIS_SCROLL`、`onGenericMotion` 任何处理，正文放在普通 `ScrollView` 里。

- 实测方向键可滚：3 次 `DPAD_DOWN` 后截图 md5 从 `03b066de` 变为 `b1e260a6`，首屏从「斗之，三段！」变为「自嘲，紧握的手掌…」；
- 滚动轴事件在虚拟屏宿主上注不进去，无法验证；ColorOS 若把表冠投成滚动轴，原来一定不滚。

修法（`ui/Widgets.kt` 的 `scrollBody`）：接 `ACTION_SCROLL`，`AXIS_VSCROLL` 乘 60 后 `scrollBy`。所有滚动页同时受益。回归：方向键仍正常滚动。

**虚拟屏**：宿主 `initUiAutomation()` 在这台 ROM 上失败后进程被 SIGKILL（`rc=137`），且拿不到虚拟屏窗口树；看门狗判「帧冻结」后每分钟重建一次，表现为「一会重启一会重启」。已关掉 UA 初始化、抓帧改为直接读 `ImageReader`、心跳文件 `vd.hb`、看门狗停用、`vd.sh stop` 改按 pid 杀（原 `pkill -f` 会匹配到自身 cmdline 而自杀）。回归：连续 8 次点击 + 静置 45 秒，`displayId` 不变，截图 18–45 KB 且内容各不相同。

## 九、未修与未验证

**未修（设计取舍）**：

1. 卡死的请求线程不回收，等系统 socket 自己超时。cached 池保证它不阻塞任何作业，但极端情况下线程数会短时增长。
2. 历史作业的 `job.json` 里 `RUNNING` 仍按「崩溃中断」处理（改判 `PAUSED`）。只有新产生的取消会写 `CANCELLED`。

**未验证**：

1. 真实表冠：这台机器是手机，表冠事件只能靠系统映射推断；滚动轴路径未实测。
2. 8 线程：只验了 3、4 线程。
3. 番茄源在高线程数下的表现（它原本固定 3）。
4. 中文搜索输入：Termux 侧剪贴板注入在本机不可用（`termux-clipboard-get` 读回为空），搜索页只验了空关键词路径。
