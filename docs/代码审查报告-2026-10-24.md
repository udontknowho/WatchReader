| 顺序 | 条目 | 理由 | 改动量 |

## 1. 必须修

### M1 第三方正则没有运行期保护，一章能把 CPU 钉死

- 位置：`core/SafeRegex.kt:27-31`、`core/Rule.kt:235-243`、`core/SourceEngine.kt:476-487`
- 是什么：`SafeRegex` 只包了 `runCatching { Regex(p) }`，管编译失败，不管运行。
- 触发：书源 `content = "##(a+)+$"`，抓到的正文是 20 KB 重复字符，`Matcher` 指数回溯，线程永不返回。
- 加重因素：`core/Downloader.kt:124` 的章超时只是放弃等待（注释自认「被放弃的线程还在飞」），线程池是 cached pool，每章漏一个自旋线程。搜索、目录路径连超时都没有。
- 修法：编译时拒掉嵌套量词形状 `\([^)]*[+*]\)[+*]`，命中就当「没有正则」返回 null。
- 后果：手表上不是慢，是整章卡死且线程不回收。
- 核实：深读结论，代码位置已复核。

### M2 模板括号递归能把栈打穿，且 catch 不住

- 位置：`core/Template.kt:131`（`parseFactor` 遇 `(` 直接递归）、`:97`（`catch (e: Exception)`）
- 是什么：`{{(表达式)}}` 的括号深度等于递归深度。
- 触发：导入一条 `searchUrl = "{{" + "("*5000 + "1" + ")"*5000 + "}}"` 的源。`StackOverflowError` 继承 `Error` 不继承 `Exception`，`:97` 兜不住，一直抛到界面。
- 修法：`:97` 改 `catch (e: Throwable)`；`Arith` 加深度上限 64。
- 核实：深读结论。

### M3 `job.json` 先删旧文件再改名，进程被杀就整本书从书架消失

- 位置：`core/JobStore.kt:58-63`
- 是什么：

  ```kotlin
  tmp.writeText(snapshot)          // 没有 fsync
  if (dst.exists()) dst.delete()   // 先删真文件
  if (!tmp.renameTo(dst)) { ... }  // 再改名
  ```

- 触发：每下一章调一次 `persist`，一本 3 000 章的书有 3 000 次「真文件已不存在」的窗口。撞上就是 `job.json` 变零字节或消失。`listBooks()` 要求它存在才列目录，`restore()` 直接返回 null——书从书架消失，章节状态全丢，只能重取目录重下。
- 测试现状：`JobLockTest` 只验并发完整性，不覆盖此刻被杀。
- 修法：去掉 `delete()`（Linux `rename` 本身是原子替换），写 tmp 后 `fd.sync()`；`readJob` 在 `job.json` 缺失时回退读 `job.json.tmp`。
- 核实：已读原文，确认。

### M4 章节行的 itemId 没转义，那一章永远重下、导出时静默消失

- 位置：`core/Downloader.kt:261`
- 是什么：`{"itemId":"${ch.itemId}",...}`。title 和 content 都过 `quote()`，只有 itemId 裸拼。
- 触发：itemId 是书源给的链接，不可信。href 里带 `"` 或换行就写出断裂的行。`readChapters` 的正则取到截断的 id，与 `job.json` 里的对不上，每轮续传都重下这一章；`exportText` 取不到 content 就 `continue`，导出文件里这章无声消失。
- 修法：改成 `"itemId":${quote(ch.itemId)}`。
- 核实：已读原文，确认。

### M5 不支持的选择器语法被当成「匹配全部」

- 位置：`core/HtmlSelect.kt:334`、`core/RuleNode.kt:476`、`:500`、`:503`
- 是什么：`matches()` 首行 `if (sel.isEmpty) return true`。`.s1,.s5`、`TEXT` 这类不支持语法解析后正好是「属性全空、raw 非空」的段，被判为空。
- 触发：`bookList: ".result-item,.list li"` 会把全页每个元素当成一个条目。`RuleBoundaryTest` 里那条断言用的是单元素文档，碰巧通过。
- 修法：改成 `return false`，让「不支持」变成「取不到」。
- 核实：已读原文，确认。

### M6 HTTP 响应没有大小上限，一个大响应直接 OOM

- 位置：`core/Http.kt:244-259`、`core/JsEngine.kt:344-352`
- 是什么：`readAll` 一路往 `ByteArrayOutputStream` 里写，`fetch` 的硬超时只限时间不限字节。暴露给书源脚本的 `java.get` / `java.ajax` 走同一条路。
- 触发：站点返回几百 MB，或「全文阅读」页把整本塞一页 → `OutOfMemoryError`，下载进程被杀，`job.json` 停在 RUNNING，用户白等一轮。
- 修法：`readAll` 加 `MAX_BYTES = 32 MB`，超限抛 `IOException`，走正常的单章失败路径。
- 核实：JS 侧已读原文；HTTP 侧为深读结论。

### M7 279 条书源是明文 HTTP，正文可被中间人整篇替换

- 位置：`app/AndroidManifest.xml:21`、`core/Http.kt:129-210`、`:213`
- 是什么：`usesCleartextTraffic="true"`，`fetchNow` 不限 scheme，`resolve()` 不拦 `Location` 里的 http。实测源库 780 条中有 279 条以 `http://` 开头。
- 触发：公共 Wi-Fi 下被劫持，用户读到攻击者写的文本，且已落盘、无摘要可比对。附带可被塞超大响应打 OOM（见 M6）。
- 修法：http 请求先试一次同地址 https，成功则用；失败的明文源在列表标注「明文」，不静默下载。
- 核实：manifest 已读原文；源库统计来自深读。
- 待定：标注口径会改变界面显示，需产品确认。

### M8 主线程被整屏重建和全量读盘挤满

- 位置：`MainActivity.kt:780`（`root.removeAllViews()` 整屏重建）、`:800`（`Downloader.restore` 在主线程）、`:516-553`（首页每个作业 `restore` 一次）、`:759-770`（目录全量建 View）
- 是什么：`showProgress` 每次重建全部视图，然后读 `job.json`（同一快照解析两次）＋整个 `chapters.jsonl`（逐行跑正则）。首页对每个作业做一遍 `restore`。目录页 `forEachIndexed` 直接给全部章节建 View，1 600 章约 6 400 个。
- 触发：进度广播每章发两次，即每秒数次，每次读数 MB。看进度屏掉帧；8 本书的首页启动白屏数秒；4 000 章的目录直接 ANR。
- 修法：进度屏只保留文字、进度条、副标题三个 View 的引用，广播时只改属性；首页只读 `job.json` 算 `count(DONE)`；目录先渲染 `lastRead ± 100`，底部「加载更多」。
- 核实：已读原文，确认。

### M9 `urlShaped` 四条分支全 `return true`，搜索地址校验是死的

- 位置：`core/LegadoImport.kt:311-323`，调用点 `:118`
- 是什么：函数体没有一条有效判定，`:320` 的域名检查和 `:322` 的兜底注释都是死代码，`:118` 的「搜索 URL 不是绝对地址」分支永远进不去。
- 触发：导入 `searchUrl = "abc def"` 的源，界面显示 ✓，`search.url` 变成 `https://a.com/abc def`，每次搜索抛 `MalformedURLException`。
- 修法：删掉两处提前 `return true`，末行改 `return false`。改完先跑 `test/EngineTest.kt:495-514` 那两组回归。
- 核实：深读结论，位置已复核。

### M10 属性值里出现 `>` 时标签边界错位

- 位置：`core/HtmlSelect.kt:119`（`val gt = html.indexOf('>', lt)`），波及 `:144` `parseAttrs`、`:182` `unclosedEnd`
- 是什么：找开标签结尾只看第一个 `>`，不看引号。
- 触发：`<div class="a" title="x > y">正文</div>`，`div@text` 得到 `y">正文`，`div@title` 得到空串。
- 修法：加一个 8 行的 `tagEnd(html, lt)`，遇 `"`/`'` 跳到配对引号，两处共用。
- 核实：深读结论。

## 2. 应当修

### S11 `ownText` 只返回第一个子元素之前的文字

- 位置：`core/HtmlSelect.kt:405`（`depth++` 从不减小）、`:376-379`（叠了一层 `replace(Regex("(?s)<[^>]*>.*"), "")` 的补丁）
- 触发：`<p>你好<span>x</span>世界</p>` 取 `p@ownText` 得 `你好`，正确值是 `你好世界`。
- 修法：识别 `</` 时 `depth--`；删掉那个 replace 补丁。

### S12 `fetchRaw` 没有总时限，注册接口一卡，整本书停在「准备下载」

- 位置：`core/Http.kt:66`、`core/DeviceRegister.kt:134`
- 是什么：`fetchRaw` 只有 connect/read 超时，没有 `fetch` 那套 `FutureTask` 硬超时。
- 触发：慢速吐字的服务器单次 read 永不超时。这一步在 `Downloader.run` 之前，章超时管不到；`ACTION_CANCEL` 的 `interrupt()` 打不断阻塞的 socket 读，用户只能杀 App。
- 修法：复用 `fetch` 的超时外壳。

### S13 通知权限从不申请，通知也没有点击意图

- 位置：`MainActivity.kt:2038`（全工程唯一的 `requestPermissions`）、`DownloadService.kt:292-315`
- 是什么：manifest 声明了 `POST_NOTIFICATIONS`，代码里没有任何地方申请；通知没设 `setContentIntent`。
- 触发：Android 13+ 首启，通知栏空白，而界面 `:746` 明确叫用户「进度看通知」；有权限时点通知也没反应。
- 修法：`onCreate` 里 `SDK_INT >= 33` 申请一次；通知加指向 `MainActivity` 的 `PendingIntent`。

### S14 `downloading` 只在广播里复位，漏一次就永久卡住

- 位置：`MainActivity.kt:1783`（判断）、`:2101`（唯一复位点，在 `progressReceiver` 内）
- 是什么：接收器只在 `onResume`~`onPause` 之间注册。
- 触发：点下载 → 退回目录 → 按 Home（注销接收器）→ 服务被杀 → 回 App 见「继续下载」→ 点下去 `startDownload` 直接 `return`，界面停在「下载中 0 章」再不动，只能杀进程。
- 修法：删掉这个内存标志，判据改用 `DownloadService.runningBookId == info.bookId`（`:737` 已这样用）。

### S15 导入没有大小和深度上限，OOM/SOE 被吞成「0 条」

- 位置：`core/SonovelImport.kt:140`、`:149-178`、`:211`、`core/LegadoImport.kt:30`、`:66`
- 是什么：几 MB 输入同时存在原文、`clean` 输出、`removeTrailingCommas` 输出三份字符串，深度不设限；`JsonParser.parse` 在顶层、不在逐条 `runCatching` 内，`catch (e: Exception)` 接不住 `StackOverflowError` / `OutOfMemoryError`。
- 触发：5 MB 或 5 万层嵌套的源库文件，最终表现是「解析出 0 条（多半拉到了 404 页面）」，真实原因被掩盖。
- 修法：入口加 8 MB 上限；`Parser` 加 `depth > 200` 抛异常。

### S16 导入的错误全部静默

- 位置：`core/SonovelImport.kt:30`、`:34-74`、`core/LegadoImport.kt:32-33`
- 是什么：sonovel 的 `importOne` 不做任何必填校验，`issue` 固定写 `null`，`usable` 按「解析出对象」计数；legado 遇到 `bookSourceName` 缺失直接 `mapNotNull` 丢掉，不计数不留痕。
- 触发：12 条 so-novel 源里 5 条带 `@js`，正文选择器被清空仍显示 ✓ 可用，下载每章空；字段写错的条目凭空消失，界面报的却是「拉到了 404」。
- 修法：对齐 `LegadoImport.Imported.issue` 的既有做法，把缺字段记成 issue 带出去。
- 待定：会改变界面上的「可用」计数，需产品确认。

### S17 TinyJson 按 key 找数组时不跳字符串

- 位置：`core/TinyJson.kt:60-62`、`:264-266`
- 是什么：`indexOf("\"key\"")` 再 `indexOf('[', at)`，`[` 落在字符串值里就被当成数组起点。
- 触发：`{"items":"[0]","data":{"items":[{"a":1}]}}` 调 `objects(body,"items")` 返回空表。`"page":"[1,2]"` 这类字段真实接口很常见。
- 修法：改走已有的 `pathOffset`（`arrayField` 已经这么做），或命中位置在字符串内时继续往后找。

### S18 榜单把「解析失败」当成「今天没数据」，且 pages 缺省被吃

- 位置：`core/RankSource.kt:253-273`、`core/RankConfig.kt:201`、`:19-22`
- 是什么：数组路径对不上返回空表 → 判成软失败 → 重试 3 次（退避 1.8 秒）→ 返回空列表。`pages` 缺省 0，而 `loadOneRank` 对非起点榜强制 `pages = 1`。
- 触发：站点改字段名后界面显示「暂无推荐」，与真的没榜无从区分；照文档示例写的起点榜只得 20 本（内置是 200 本）；番茄更新榜写 `pages:5` 也只出 20 条。
- 修法：`arrayField` 区分「没有该路径」与「空数组」，前者抛错；`pages` 按 kind 给默认值（起点 10、番茄更新 5）。

### S19 没有 `onSaveInstanceState`，进程被杀后重建落回首页

- 位置：`MainActivity.kt:425-433`（`onCreate` 忽略 `savedInstanceState`，全类无 `onSaveInstanceState`），`screen` 只活在内存 `:153`
- 是什么：`configChanges` 挡住了旋转，挡不住进程回收。
- 触发：读到第 300 章，切出去十分钟被系统杀，回来在首页，要重新搜书名进目录才轮得到「继续读」。
- 修法：`onPause` 里存 Reader 的 bookId 与 index，`onCreate` 里直接恢复。

### S20 两条 UI 测试是自造副本，挡不住上面任何一条

- 位置：`test/AsyncGuardTest.kt:19`（注释原文「与 MainActivity.postAlive 同一套判据」）、`test/NavProgressTest.kt`
- 是什么：测试里重新实现了 `postAlive`、`setScreen`、`readProgress`，不引用 `MainActivity` 的任何函数。
- 后果：M8、S14、S19 改坏了测试照样全绿。
- 修法：把这两个判据抽成 `internal` 顶层函数，测试调真的那份。

- manifest 的 `foregroundServiceType="dataSync"` 与 `exported` 都已声明，targetSdk 34 的前台服务要求满足。

# 第二批审查（2026-10-25 补）

## 7.2 新发现

### N1 单章取数的线程池没有上限，超时的线程不回收

- 位置：`core/Downloader.kt:238`（`Executors.newCachedThreadPool`）、`:243-258`（`withChapterTimeout`）
- 是什么：cached pool 在新任务到来时无限建线程。超时走 `f.cancel(true)`，而注释自己承认「Java 无法可靠地中断阻塞中的 socket 读，`cancel(true)` 多半无效」。
- 触发：一本 3000 章的书遇到 200 个慢章。每次超时留下一个仍在跑的线程，池里同时存活的线程数累积。每条线程持有响应缓冲和 socket。手表上 200 条线程 + 各自的缓冲，直接 OOM 或 `OutOfMemoryError: unable to create native thread`。
- 修法：换 `newFixedThreadPool(concurrency + 2)` 并给提交加 `Semaphore`；或超时后把该源标记为「慢源」，降级为串行。
- 核实：已读原文。

### N2 导出先清空目标文件再写，中途被杀就把旧导出文件毁了

- 位置：`core/Downloader.kt:400-410`（`RandomAccessFile(out, "rw")` + `setLength(0)`）
- 是什么：先截断到 0，再逐段写。转换阶段（`convert`）在截断之后、写入之前完成，写入过程中的任何异常或进程死亡都留下一个半截文件，原来的完整导出已经被清空。
- 触发：导出 2000 章的书，写到一半 ColorOS 杀进程，用户手上的 `.txt` 从完整变成残缺，且无法恢复（源是 `chapters.jsonl`，能重新导，但用户不知道）。
- 修法：写 `out.name + ".tmp"`，成功后 `rename`。三行。
- 核实：已读原文。

### N3 下载结果只统计本次运行，续传后界面报「成功 5 失败 0」

- 位置：`core/Downloader.kt:225`（返回值）、`DownloadService.kt:268`
- 是什么：`Result(ok, fail, job.chapters.size)` 里 `ok` 是本次新下的章数，`total` 是全书章数。续传时只下 5 章，就报「成功 5 失败 0」，而书里已有 1200 章。
- 触发：中断后点「继续下载」，结束时提示「成功 5 失败 0」，用户以为只下了 5 章。
- 修法：`ok` 用 `statuses.count { it == DONE }` 算全书已下载数，另加一个 `runOk` 表示本次新增。
- 核实：已读原文。

### N4 分页与脚本的 baseUrl 传错，拼出错误地址

- 位置一：`core/SourceEngine.kt:455` —— `absolute(...)` 没传 base，默认用 `rule.host`，注释却写「相对当前页求值」。
  - 触发：章节页 `/book/123/456.html`，下一页取到相对链接 `456_2.html` → 拼成 `/456_2.html`。404 就被吞掉、正文停在第 1 页；站点根返回 200 时首页文字被拼进正文。
- 位置二：`core/SourceEngine.kt:373` —— 目录列表脚本 `evalList(raw, lst, "", rule.jsLib)` 的 `baseUrl` 是空串，搜索路径传的是实际 url。
  - 触发：源库里有 12 条 `chapterList` 是纯 `<js>` 且用 `baseUrl`（如 `list=[{text:"第1页",href:baseUrl}]`）→ href 得空串 → 回退成目录页地址当章节链接 → 正文取到目录页。
- 修法：两处都把当前页地址传进去。
- 核实：深读结论。

### N5 正文取不到时，整页 HTML 当正文存下，章节算成功

- 位置：`core/SourceEngine.kt:434`（`if (all.isEmpty()) return raw`），入口 `:411`
- 是什么：站点改版、选择器失效、脚本报错，全部落到「返回原始 HTML」。
- 触发：某源正文选择器不再命中 → 每章存整页 HTML（导航、广告、版权），`Downloader.kt:125` 的 `html.isBlank()` 不成立，记 DONE。结果全书「成功 N 失败 0」，导出文本全是菜单。用户要到打开文件才发现。
- 修法：规则有选择器却取空时返回 `""`，交给上层现有的「正文为空」记 FAILED。
- 核实：深读结论。

### N6 失败被静默降级成「正常结果」

- 位置一：`core/SourceEngine.kt:321` —— 目录预算耗尽只 `break`，`toc()` 照常返回已有章节，无标志。触发：6 页目录第 6 页超时 → 返回前 5 页 → 后续标 DONE，书少几十章。
- 位置二：`core/MultiSource.kt:97`、`102-110`、`119` —— 超时任务在 `onFailure` 记一次失败，`isCancelled` 分支再记一次；`responded = sources.size - failed.size` 可为负。15 个源全挂时界面给的是「没有找到，换个关键词试试」——断网时建议是错的。
- 修法：目录截断抛 `IOException("目录不完整")` 让换源逻辑接住；`failed` 换 `Set`、`responded` 用独立计数器，`responded == 0` 时界面改说「全部源无响应」。
- 核实：深读结论。

### N7 同名书源会选错站

- 位置：`core/MultiSource.kt:205`（`pool.firstOrNull { tidySourceName(it.name) == n }`），注册点 `MainActivity.kt:60`
- 是什么：只按显示名匹配，重名时永远命中第一条。
- 触发：源库实测 **88 组重名**。`漫客栈` 同时有 `comic.mkzhan.com` 与 `www.mkzhan.com`；`酷我小说` 三条不同接口。选 B 站的书，交给 A 站引擎取目录 → 空目录 → 报「取不到目录」。去掉装饰符后还会再撞（`" 绾书文学"` 与 `"绾书文学"`）。
- 修法：注册时给重名追加 host 后缀，`pickFor` 保持精确匹配。
- 核实：深读结论，数字来自本地源库统计。

### N8 云端配置：旧版本能覆盖新缓存，镜像串行且超预算

- 位置：`core/RankConfig.kt:143-160`、`167`、`core/CloudSource.kt:132-137`
- 是什么：
  1. `parse()` 不读 `version`，`load` 取第一个能解析的镜像就落盘覆盖，没有「取最高版本」的逻辑。设备缓存是 v4，先命中滞后的 gcore 节点（v2）就写回 v2 → 榜单列表两次进入之间抖动。
  2. `File(dir, FILE_NAME).writeText(...)` 非原子写，进程被杀留半个 JSON → 解析失败 → 静默退回 `BUILTIN`。
  3. `bestMirror` 串行问 4 个镜像，且 `deadline` 在它之后才算。4 个域名都挂住时 4×8 秒 + 后续 45 秒 ≈ 77 秒，与注释宣称的 45 秒预算不符。
- 修法：`parse` 返回 version 并只在更高时覆盖；写 tmp 再改名；`deadline` 提前并传入 `bestMirror`。
- 核实：深读结论。

### N9 全部章节塞进一个 Intent extra，点下载直接闪退

- 位置：`DownloadService.kt:76-88`（`EXTRA_CHAPTERS`）
- 是什么：整个目录 join 成一个字符串走 Binder，硬上限 1 MB。
- 触发：通用书源 `itemId` 是完整 URL（60–90 字符），一行约 82 字符，6000 章 ≈ 1 MB。超限时 `startForegroundService` 抛 `TransactionTooLargeException`，抛在 `startDownload` 的主线程 → 点「下载」直接闪退。代码里没有章节数上限。
- 修法：`EXTRA_*` 只传 `bookId/name/author/freeOnly`，章节由服务自己从 `job.json` 或书源取。
- 核实：深读结论；1 MB 是按 UTF-16 估算，未用真实目录实测。

### N10 服务的进度计数与状态回报自相矛盾

- 位置：`DownloadService.kt:222-255`（`done`/`failed` 是普通 Int，3 个并发线程各自 `done++`）、`:126-131`（重复 start 静默丢弃并把通知打回 0/0）、`:268`/`:272`（取消后先报「下载完成」再报「已取消」）
- 是什么：三处独立缺陷，都会让界面数字或结论与实际不符。取消那条最刺眼：`dl.run()` 取消时是正常返回，于是无条件 `publish("下载完成…", finished = true)`，`finally` 才补「已取消」。
- 修法：`AtomicInteger`；重复 start 存进 `AtomicReference` 由收尾 Runnable 接着跑；`if (!cancelFlag.get()) publish("下载完成…")`。
- 核实：深读结论。

### N11 全程没有 wakelock，与界面文案矛盾

- 位置：`DownloadService.kt:207-278`（只有 `startForeground`）
- 是什么：前台服务保证进程不被降级，不保证 CPU 不休眠。
- 触发：锁屏后进入 suspend，`Thread.sleep(80)` 与网络回包被拉长到秒级；而进度页明写「下载在前台服务里跑，锁屏不会断」。
- 修法：`runJob` 开头 `PARTIAL_WAKE_LOCK.acquire()`，`finally` 里 `release()`。
- 核实：深读结论，未在设备上锁屏实测。

### N12 测试挡不住回归：一条恒真、三处副本、一处硬编码绝对路径

- `test/EngineTest.kt:722` —— `runCatching { eng.toc(...) }` 把返回值和异常都丢掉，随后断言 `hits <= 32`。改坏分页解析让第一页就抛异常时 `hits == 1`，断言依旧成立。这是「目录分页封顶」的唯一断言。
- `test/FinishTest.kt:45`、`test/RotationTest.kt:18`、`test/P0RegressionTest.kt:80` —— 把 `score()`、`next()`、`listBooks()` 的过滤逻辑就地重写一遍再断言副本。真实现改成任何样子都绿。
- `test/FinishTest.kt:71` —— 硬编码绝对路径 `/data/data/com.termux/files/home/WatchDownloader/build.sh`。**更正：`WatchReader` 是 `WatchDownloader` 的符号链接，两者是同一个仓库**，所以这条当下是对的，不构成 bug。真问题是路径写死：仓库搬家或改名后这条断言会抛 `FileNotFoundException`，整个测试挂掉而不是跳过。
- 修法：三处调真实现（反射已经用上了，可达性不是障碍）；`EngineTest` 先断言 `isSuccess`；路径改相对 `build.sh`（`P0RegressionTest` 已经这么读 `src/…/MainActivity.kt`）。
