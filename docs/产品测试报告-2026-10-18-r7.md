## 二、P0-1 下载线程卡死

**现象**：从 179 章开始不动，8 分钟没有新增；界面停在「下载中」，通知常驻，`job.json` 仍是 `RUNNING`。

**证据**：
- `chapters.jsonl` 在 11:18 与 11:26 两次取样都是 179 行；
- `dumpsys activity services` 显示 `DownloadService` 仍在前台；
- 抓主线程栈（`kill -3`）看到 worker `Thread-22` 停在
  `Http.fetch(Http.kt:101)` → `getResponseCode`，即卡在读响应阶段。

**根因**：`readTimeout` 只约束单次读。服务器持续慢速吐字节时它永远不触发，请求可以无限拖。

**修法**（`Http.kt`）：每次请求起一个看护线程，`timeoutMs × 2` 到点后从外部 `conn.disconnect()` 打断读，并抛 `请求超时（Nms）`。上层 `Downloader` 照既有退避逻辑记一次失败并重试。

**回归**：新增 `HttpTest` 用例「慢速吐字会在总时限内失败」——本地起一个每 300 ms 吐 1 字节的服务，断言 3 秒内失败。通过。

## 三、P1-2 取消后状态没落盘

**现象**：点「取消」后下载确实停了（`chapters.jsonl` 冻结在 270 行、服务记录为 0），但 `job.json` 里 `state` 还是 `RUNNING`。

**影响**：`Downloader.restore` 把 `RUNNING` 一律当成「上次异常中断」改判 `FAILED`。用户主动暂停的作业被记成崩溃，诊断和后续统计都会被误导。

**修法**：
- `Model.kt`：`JobState` 增加 `PAUSED`；
- `JobStore.writeState()`：只改 `state` 字段，其余原样保留；
- `DownloadService` 的 `finally`：取消时先落盘 `PAUSED` 再发「已取消」通知。

**实测**：点「取消」后立刻读盘，`state=PAUSED`，`chapters.jsonl` 停在 281 行不再增长；界面退回目录页，显示「已下 281 · 失败 0」，可再点「继续下载」。

**回归**：新增 `CoreTest` 用例「取消把 RUNNING 改成 PAUSED」「其余字段保留」。通过。

## 五、P1-3 规则模板没求值

**现象**：搜索结果副标题显示 `@{{$.author_nickname}} · 爱推书…`。

**根因**：源库里 106 条规则用了 legado 的 `{{$.a.b}}` 模板写法（作者、分类、字数等字段），本引擎只支持 URL 模板 `{{var}}`，于是原样返回。

**修法**（`Rule.kt`）：规则值里含 `{{$` 时，按 `$.path` 从 JSON 响应取值回填；取不到的整段丢弃，宁可留空也不把规则语法露给用户。

**回归**：
- `CoreTest` 新增三例：作者模板求值、模板夹字面量、取不到给空串；
- `E2e` 新增断言：搜索命中里任何 `name`/`author` 含 `{{` 即判失败。实跑 1714 条命中，0 条泄漏。

## 六、P1-4 e2e 自测的产物不可读

`E2e` 拿 `JobStore.readChapters()` 的返回值当正文——那其实是整行 JSONL。结果：

- `build/e2e/out.txt` 里每章正文是 `{"itemId":"…","title":"…","content":"<div …>…"}`；
- 第 6 步「正文完整」的数字数把 JSON 与 HTML 一起算进去，每章「最少 2619 字」是虚的，掩盖了正文质量。

**修法**：取 `content` 字段，再用 `Downloader.htmlToText()` 转文本（与应用导出的处理一致）。

**修后**：`out.txt` 为纯文本、带全角缩进，每章最少 2215 字（真实字数）。

## 六点五、下载服务被系统杀掉（未修）

修完 P0-1 后又复现了「下载停住」，但这次原因不同：

- `chapters.jsonl` 冻在 306 行，`job.json` 仍是 `RUNNING`，`DONE 306 / PENDING 1339 / FAILED 0`；
- `dumpsys activity services com.watchdl` 的 `ServiceRecord` 数量为 **0** —— 服务已经没了；
- 进程 `oom_score_adj=900`，即被系统降到 cached 档。

也就是说，前台 `dataSync` 服务在某些情况下仍会被 ROM 杀掉（屏幕不可见、省电策略介入）。进程被杀时 `finally` 不执行，作业就留在 `RUNNING`，界面上「下载中」停在最后一帧数字，不会提示已停止。

**没有自动续传**：`restore` 把 `RUNNING` 改判 `FAILED`，用户回到目录再点「继续下载」才会接着跑。这个设计本身没错，缺的是「已经停了」这个提示。

未修原因：修法涉及产品决策——自动续传 / 提示后一键续传 / 只在充电与前台时下载，三条路的取舍要人来定。

## 七、目录混入「最新章节」（未修）

`build/e2e` 用源「言情小说」取《斗破苍穹》目录，第 1、2 章是：

```
第一章 陨落的天才     .../read/14927_12470467.html
第一章  五帝破空      .../read/14927_12472390.html   ← 2000 多个 id 之外，实为大结局
第二章 斗气大陆       .../read/14927_12470468.html
```

即站点目录页的「最新章节」区块被一起抓进来了。1914 章里有 1 条这样的错位条目。

**为什么不直接修**：同一份目录里 `itemId` 普遍不单调（257 处逆序），按 id 跳动做过滤会误删正常章节；按标题里的「第 N 章」去重又可能误伤上下篇同名的情况。稳妥做法是按源定义目录容器，或给每个源加一个「剥离最新章节」开关——需要单独一轮。
