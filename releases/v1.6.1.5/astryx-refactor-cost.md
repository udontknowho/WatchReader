# Astryx 重构工作量评估（1.6.1.5 审查附带）

写于 2026-11-13 夜。给的是判据和数字，不是估计。

## 先说结论

Astryx 是 React 组件库，产物是 HTML/CSS；这个项目是纯 Kotlin 原生 Android，零 WebView，31 104 行界面全部由 `android.widget` 手工搭。两者之间没有直通车道。所以「按 Astryx 重构 UI」只有两条路，工作量差一个数量级：

| | 方案 A：出 Astryx 设计稿 | 方案 B：把令牌体系换成 Astryx 设计语言 |
|---|---|---|
| 交付物 | `ui/astryx-watch-v1615.html`，2.1 MB 单文件，7 屏 | 改 `Md3.kt` + `Widgets.kt` + 20 个屏文件 |
| 本轮耗时 | 已完成 | 3–4 个工作日 |
| 风险 | 零（不动源码） | 高（改 2025 处符号调用） |
| 上机验证 | 不需要 | 必须，否则是盲改 |

推荐 A 做验收基准，B 等设备的触控与耗时有实测数据之后再动。

## 为什么 B 贵：调用点密度实测

```
Md3./Widgets. 符号调用总数     2025 处
├─ Md3.dp                        507
├─ Md3.text                      157
├─ Md3.FS*（字号常量）           154
├─ Md3.onSurfaceVariant          113
├─ Md3.PAD / GAP（边距常量）     138
├─ Widgets.button                 47
├─ Widgets.emptyState / scrollBody /
│  contentColumn / topBar / longMenuDialog   182
└─ 其余色角色与工具方法           727
```

`Md3` 是**可变单例**：主题切换靠 `applyPalette()` 改静态字段，已建好的视图不会自己刷新，所以每个屏都要在换主题后整屏重建。B 方案要换掉的是这套「全局可变状态 + 视图工厂」的组合，不是换个色表。改法只有两种，两种都疼：

1. **只换 token 值**（改 `Palette` 的 16 个色角色 + 字号阶 + 圆角阶到 Astryx 的取值）
   工作量 0.5 天。不动任何调用点，2025 处一行不改。
   崩点：`Md3` 里硬编码的例外值会漏——`ok` 语义色、`nameColor()` 的四色哈希、`HEADER_H = 25` 这类用户当场定的尺寸。改了配色不改这些，界面会花。
   这是**性价比最高的一条**，但它不叫「用 Astryx」，叫「照 Astryx 的色板重新调色」。

2. **真换结构**（Astryx 的 Stack/间距标度/组件边界映射到 View 层）
   工作量 3–4 天。要有 `Widgets.kt` 1258 行的重写、20 个屏文件的逐屏对照、14 个现有测试文件的连带修改。
   崩点：Astryx 的 spacing scale（gap 2/4/5）与 `Md3.GAP=6`、`PAD=10`（手表档）不是同一套数感，逐处映射必然出现半像素累积误差；189 dp 宽的屏上 1 dp 错位肉眼可见。第二次崩点在 `Widgets.kt` 的 28 个工厂方法——它们接收 `Context` 并直接 `new View`，没有主题订阅机制，改结构等于重写这 28 个方法各自的布局约定。

## 具体成本拆分（B 方案）

| 步骤 | 内容 | 天 | 为什么这个数 |
|---|---|---|---|
| 1 | `Md3.kt` 令牌对齐（色角色、字阶、圆角、间距标度） | 0.5 | 405 行，值替换为主 |
| 2 | `Widgets.kt` 28 个工厂方法重写 | 1.0 | 1258 行，每个方法都要重算内边距 |
| 3 | 7 个主屏逐屏对照（书架/发现/搜索/详情/目录/正文/我的） | 1.5 | 6000+ 行，改一处看一眼 |
| 4 | 次级屏 8 个（缓存/替换/日志/文件/书签/记录/换源/关于） | 0.5 | 结构简单，多为列表 |
| 5 | 14 个界相关测试文件同步 + `build.sh test` 41 组跑绿 | 0.5 | 断言里写死了尺寸与颜色 |

合计 4 天。若第 3 步里出现 `Md3` 单例与已建视图不同步导致的刷新问题，每个屏再加 2 小时排查。

## 方案 A 已交付什么

`ui/astryx-watch-v1615.html`：2 152 601 字节，单文件，字体以 base64 内联，断网可看，无外链请求（`http://` 命中均为 SVG 命名空间常量与 React 错误文档前缀，不发起请求）。

7 块表盘按 `aspect-ratio: 189 / 248` 固定真实比例：① 书架 ② 发现·榜单 ③ 搜索结果 ④ 书籍详情 ⑤ 目录 ⑥ 正文阅读 ⑦ 我的·设置。组件取 Card / Button / Badge / Text / Heading / TextInput / List / Switch / ProgressBar / SegmentedControl / Divider / Icon / VStack / HStack / Theme，无手写按钮与输入框，色值全部走 token。

为 189 dp 做的三条取舍：
1. 全部组件降到 `sm`/`xsm`/`3xs`，列表密度 `compact`——Astryx 的 `md` 在 189 dp 宽里会把文字挤出屏。
2. 正文 `columns: 2` + 行高 1.62 + 两端对齐——一行只放得下 12 个汉字，单栏太宽会丢行。
3. 底部进度条 + 菜单用 `inset: auto 0 0 0` 压住，点正文才出现——常驻会吃掉两行，而两行在手表上是半屏。

## 怎么用这份稿子

把它当**验收基准**：真机（OPPO Watch 3 Pro，189×248 dp）跑起来之后，逐屏对照这 7 块表盘。凡是「稿子上放得下、机上放不下」或反过来的地方，记下来，那才是要改的清单。先有清单再动 `Widgets.kt`，比先动 `Widgets.kt` 再找问题省一半时间。

## 本文档不含

- 没有改版本号、没有打 APK、没有发布、没有安装、没有启动应用。
- 没有动 `Md3.kt` / `Widgets.kt` 任何一行。B 方案要动，等你说。
